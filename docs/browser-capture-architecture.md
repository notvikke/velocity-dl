# Browser Capture Architecture

## Audit outcome

The previous bridge detected many media URLs, but it did not preserve the request that produced them. Browser takeover synthesized `Referer` and `Cookie`, dropped POST bodies, did not retain redirect chains, and launched one native host process per message. Network sniffing discarded `.ts`/`.m4s` segments, while the isolated content script could not observe page-owned `fetch`, XHR, MediaSource, blob creation, or closed shadow roots. The native contract silently ignored any future request metadata and the downloader always issued GET.

## Implemented capture pipeline

1. `webRequest.onBeforeRequest` records method, body, tab/frame identity, initiator, document URL, and the initial URL.
2. `onBeforeSendHeaders` with `extraHeaders` records the browser's actual reproducibility headers, including User-Agent, Referer, Origin, Authorization, Cookie, Accept headers, and signed custom headers. Hop-by-hop and transport-managed headers are removed.
3. Redirect, completion, and error events update the same bounded request record. Records expire after ten minutes and the store retains at most 500 entries.
4. At handoff time, the exact/same-tab request is selected and current URL-scoped cookies replace stale captured cookies. POST form data and binary bodies are represented as UTF-8 or Base64 and capped at 512 KiB; oversized bodies are explicitly marked unavailable rather than truncated and replayed incorrectly.
5. The payload crosses native messaging with method/body, network request id, frame metadata, initiator/document URL, redirect chain, capture timestamp, and media context. The Rust host validates methods, body encoding, size, and URL before queueing it.
6. Direct POST downloads use a single non-ranged request and replay the captured bytes. GET downloads retain range segmentation and resume behavior.

## Media embedding matrix

- HLS and DASH manifests are observed at both Chromium network level and page JavaScript level.
- `.ts`, `.m4s`, CMAF, and fMP4 fragments are retained as bounded diagnostic groups instead of being discarded.
- A document-start MAIN-world observer instruments fetch, XHR, object URL creation, MediaSource, SourceBuffer, resource timing, DOM media sources, and `attachShadow`.
- An isolated all-frame bridge validates and forwards observations. `all_frames` plus `match_origin_as_fallback` covers permitted nested frames, including `about:blank`, `data:`, and blob-origin child frames derived from an allowed parent.
- Blob/MSE observations are associated with the latest same-frame manifest/direct media and segments; blob URLs themselves are never handed to the native downloader as if they were network URLs.

## IPC and bulk behavior

The extension now uses one lazy persistent native port. Requests have transport correlation IDs, bounded in-flight concurrency, FIFO backpressure, 90-second timeouts, disconnect rejection, and automatic reconnect for queued work. This keeps bulk handoffs asynchronous and prevents a capture burst from blocking the MV3 event loop.

## Session refresh sequence

When a browser-origin direct download receives 401 or 403, the downloader writes an atomic, expiring refresh request containing the URL and original network request ID. A 30-second MV3 alarm (also run at startup/heartbeat) drains pending requests. The extension obtains current URL-scoped cookies, combines them with the latest captured request headers, and returns an atomic one-time response. The downloader replaces allowed headers and retries once. Requests expire after two minutes and downloader waits are bounded to 70 seconds.

## Security and privacy boundaries

- Cookie, Authorization, signed headers, and request bodies stay in the local extension/native-host/app path and are not logged.
- Header names/values are validated against injection; Host, Content-Length, connection, transfer, and compression transport headers are regenerated by the HTTP client.
- Native messages are limited to 4 MiB and captured bodies to 512 KiB.
- Refresh files use random identifiers, atomic rename, one-time consumption, and short expiry.

## Platform limits

“Any website” cannot be guaranteed by a browser extension. The following are intentionally not bypassed:

- DRM/EME streams (Widevine, PlayReady, FairPlay) and decrypted media keys.
- Opaque service-worker responses or bytes generated entirely inside a worker/WASM pipeline without observable network URLs.
- One-use URLs/tokens that are invalidated server-side before the native request and cannot be refreshed by cookies alone.
- Cross-origin frames for which Chromium withholds host access, enterprise policy blocks, browser-internal pages, and extension stores.
- POST bodies larger than 512 KiB, streaming uploads, filesystem uploads, or request bodies Chromium reports as unavailable.

Within those browser security boundaries, the bridge now preserves the complete reproducible context Chromium exposes instead of claiming success with a weakened request.
